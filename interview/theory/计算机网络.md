#### TCP 三次握手和四次挥手

##### TCP 三次握手

```text
第一次握手：客户端 → 服务端
    客户端发送 SYN=1，携带客户端初始序列号 seq=x，请求建立连接。
    客户端状态：SYN_SENT

第二次握手：服务端 → 客户端
    服务端回复 SYN=1, ACK=1；
    确认号 ack=x+1（确认收到客户端报文），同时携带服务端初始序列号 seq=y。
    服务端状态：SYN_RCVD

第三次握手：客户端 → 服务端
    客户端发送 ACK=1，确认号 ack=y+1。
    客户端状态：ESTABLISHED（连接已建立）
    服务端收到后：ESTABLISHED
```

就像王者荣耀建立亲密关系：我要建立关系，收到你的申请同意，收到“同意”

* 为什么不是两次握手？

防止失效的连接请求报文到达服务端，导致服务端无故维护无效连接，浪费资源。

##### TCP 四次挥手

TCP 连接是全双工（双方可同时收发），因此读写通道要分别关闭，需要四次交互

```text
第一次挥手：主动方 → 被动方
    主动方发送 FIN=1，表示本方不再发送数据，请求关闭本方写通道。
    主动方状态：FIN_WAIT_1

第二次挥手：被动方 → 主动方
    被动方回复 ACK=1，确认收到关闭请求。
    主动方状态：FIN_WAIT_2（不再发数据，但仍可接收数据）
    被动方状态：CLOSE_WAIT

第三次挥手：被动方 → 主动方
    当被动方数据全部发送完毕，发送 FIN=1，关闭本方写通道。
    被动方状态：LAST_ACK

第四次挥手：主动方 → 被动方
    主动方回复 ACK=1 确认。
    主动方等待 TIME_WAIT（2MSL），确保对方收到最后 ACK，再进入 CLOSED
    被动方收到 ACK，直接进入 CLOSED
```

我要关闭我的通道，你关吧。
我也要关闭我的通道，你也关吧。

#### TCP 如何保证传输的可靠性？

序号 + ACK、超时重传、去重、校验和、流量控制、拥塞控制、连接管理、乱序重排

#### 从输入 URL 到页面展示到底发生了什么？

DNS 解析 → TCP 连接 → (HTTPS 加密握手) → 发请求 → 服务器响应 → 断开连接 → 浏览器解析渲染页面
