# 操作系统

#### 说说线程的生命周期和状态?

```mermaid
stateDiagram-v2
    direction TB
    New: 新建(New)
    Ready: 就绪(Ready)
    ReadySuspend: 挂起就绪<br>(内存外，等待调度)
    Running: 运行(Running)
    Blocked: 阻塞(Blocked)
    BlockedSuspend: 挂起阻塞<br>(内存外，等待条件)
    Terminated: 终止(Terminated)

    %% 新建流转
    New --> Ready : 初始化完成，加入就绪队列

    %% 就绪 <--> 运行
    Ready --> Running : CPU调度，分配时间片
    Running --> Ready : 时间片耗尽/高优先级线程抢占

    %% 运行 -> 阻塞 / 睡眠
    Running --> Blocked : 等待IO/等待锁/调用sleep进入睡眠

    %% 阻塞唤醒回到就绪
    Blocked --> Ready : IO完成/锁释放/睡眠时间到，唤醒

    %% 系统挂起：就绪态 → 挂起就绪
    Ready --> ReadySuspend : 内存不足/系统调度，执行挂起
    %% 解挂：挂起就绪 → 就绪
    ReadySuspend --> Ready : 内存充足，解除挂起

    %% 系统挂起：阻塞态 → 挂起阻塞
    Blocked --> BlockedSuspend : 内存不足/系统调度，执行挂起
    %% 解挂：挂起阻塞 → 阻塞
    BlockedSuspend --> Blocked : 内存充足，解除挂起

    %% 挂起阻塞 条件满足 → 挂起就绪
    BlockedSuspend --> ReadySuspend : 阻塞条件解除(IO/睡眠结束)

    %% 线程终止
    Running --> Terminated : 代码执行完毕/异常退出
```

顺便一提：底层是操作系统内核线程被挂起，但 JVM 层面不感知；
即便是kotlin的suspend也是线程内部的协程级别的挂起。


#### 分段机制、分页机制描述一下

前置基础：虚拟地址 & 物理地址

分页、分段，本质都是把虚拟地址翻译成物理地址的内存管理方式，解决内存分配、碎片、权限、地址隔离问题。

* 分段机制（Segmentation）
  - 把进程的逻辑地址空间，按照程序逻辑模块划分为若干段。

* 分页机制（Paging）
  - 把虚拟地址空间和物理内存，都固定大小划分为一个个页（Page） / 页框（Page Frame，物理页）


* JNI层直接new一个100MB的空间失败，而且用largeHeap也失败:
  - 进程虚拟内存存在大量外部碎片，没有连续的 100MB 空闲地址区间，所以分配大块连续内存失败；largeHeap 只是放大堆总上限，解决不了「连续空间不足」的问题。
