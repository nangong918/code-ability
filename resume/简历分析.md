# 简历分析


## IJetty嵌入式上位机服务端

### IJetty在系统中的职责是什么？

主要是控制透传，web发送的json指令要解析成RK芯片能看懂的V协议指令。

并且将RK上行的指令组装成WebSocket交给局域网Web前端；或者组装成MQTT交给云上服务SpringBoot。

### IJetty是怎么提供Http请求和WebSocket主动上推这些服务器的能力的？

Linux Socket，外加 Jetty 自己的 NIO 线程池、协议解析、连接管理、WebSocket 升级 / 帧收发

### 高负载探卡 OOM 与 GC 卡顿问题问题的产生原因是怎样的？你解决的方案是什么？

我们的Android程序是调用公司SDK开发组的接口，SDK开发组会将数据整理成JSON直接上行。
原先的方案是在JNI层直接用jstr创建60MB然后拷贝到Java层用String接收然后写入到JSON。

但是后续进行压力测试，尝试了2w张接收卡的测试，发现一次回复的JSON数量太大了，
本来就是高负载环境，内存压到极限的情况下突然申请60MB的整块内存导致内存压力过大，
导致没有多余的内存空间分配给其他变量，其他的弱引用、虚引用以及垃圾就频繁回收。
并且在4w张卡的时候直接出现了OOM。

解决方案，我首先是不在JNI层直接创建60MB，而且60MB也接收不了4w张卡，根据JSON计算，
4w张接收卡的JSON大小大概在100MB，所以采用了碎片传输。
在JNI层每次malloc 128KB的存储块，然后逐片传输给Java层。
Java层最开始还是用OutputStream接收然后写入JSON，但是发现还是比较慢，
就直接使用DirectBufferOutputStream接收，减少拷贝次数，
最后直接写入JSON传递给前端，解决了OOM和频繁GC卡顿。

### AIDL云上接口是怎样设计的

设计指令调用Bean，需要继承Parcelable：
```java
package com.uber.server;

import android.os.Parcel;
import android.os.Parcelable;

public class HardwareCommand implements Parcelable {
    // 指令类型：1开闸 2关闸 3探卡 4状态上报
    public int cmdType;
    // 设备ID
    public String deviceId;
    // 时间戳
    public long timestamp;
    // 扩展数据：你的4w张卡二进制数据、JSON片段、DirectBuffer数据都放这里
    public byte[] extendData;

    // ==========================================
    // 以下是 Parcelable 固定实现（AIDL 必须）
    // ==========================================

    public HardwareCommand() {}

    protected HardwareCommand(Parcel in) {
        cmdType = in.readInt();
        deviceId = in.readString();
        timestamp = in.readLong();
        extendData = in.createByteArray(); // 读取 byte[]
    }

    public static final Creator<HardwareCommand> CREATOR = new Creator<HardwareCommand>() {
        @Override
        public HardwareCommand createFromParcel(Parcel in) {
            return new HardwareCommand(in);
        }

        @Override
        public HardwareCommand[] newArray(int size) {
            return new HardwareCommand[size];
        }
    };

    @Override
    public int describeContents() {
        return 0;
    }

    @Override
    public void writeToParcel(Parcel dest, int flags) {
        dest.writeInt(cmdType);
        dest.writeString(deviceId);
        dest.writeLong(timestamp);
        dest.writeByteArray(extendData); // 写入 byte[]
    }
}
```

将Java对象转为AIDL的接口`HardwareCommand.aidl`
```aidl
package com.uber.server;

parcelable HardwareCommand;
```

下发指令：
```aidl
package com.uber.server;
import com.uber.server.HardwareCommand;
import com.uber.server.IHardwarePushCallback;

interface IHardwareControl {
    // 下发指令：云端 → 上位机
    int sendControlCommand(in HardwareCommand command);

    // 注册主动上推回调（关键：像 WebSocket 一样长连接）
    void registerPushCallback(IHardwarePushCallback callback);

    // 解注册
    void unregisterPushCallback(IHardwarePushCallback callback);
}
```

回读指令：
```aidl
package com.uber.server;
import com.uber.server.HardwareCommand;

interface IHardwarePushCallback {
    // 主动推送：硬件状态变化
    void onHardwareStatusChanged(in HardwareCommand status);

    // 主动推送：探卡数据（4w张卡）
    void onReceiveCardData(in HardwareCommand cardData);

    // 主动推送：事件上报（报警/心跳/结果）
    void onHardwareEvent(int eventType, in String msg);
}
```

### RK3588和RK3399的升级兼容你是怎么做的？

RK3399是老Android 9 平台，挂在目录是在 `/dev` 是真实的设备
RK3588是新的Android 12 挂在的是 虚拟块设备 /dev/block/dm-0、dm-1、dm-2这种
所以改成了挂在/dev/dm-1

然后解决了整包升级问题，原因就是之前我们公司打包的整包升级里面RK程序和Android的服务器程序升级是异步的，
都去remount w写，然后自己升级完成就改成remount o读，导致另外个升级失败，后续改为了取消remount o读

### 怎么优化 Dante 音频板卡超大场景存储：针对双网口的 128 通道预置场景超 V 协议帧限制问题，将配置迁移至服务端 SQLite 持久化存储，解决传输与存储瓶颈

首先当时没有进行压力测试，后续压力测试的预置场景数量非常的大，
RK的设计是智能发下65532字节，导致一次拿不完，就将预制场景放在了Android服务器，存储在SQLite。

### 解决高负载问题怎么解决的？

首先高负载会出现很多卡死，因为低下的RK是串行操作，
原先数据量小就传递很快，现在数据量大了之后就传递的非常慢，
然后我跟RK一起设计了进度上推，让用户知道进度。


## Cross集群管理App

### Cross怎么实现主机掉线备机顶上的

他们之间在使用3秒轮询的UDP组播discover，如果如果主机掉线web就会改为跟备机通信。
备机就会顶上。

### 开发分布式集群
多设备组成设备集群，每个这杯负责不同的画面，整体组成一个大画面集群

### 重构设备间Discovery发现
原先的mDNS协议不适合3秒心跳，只是在设备两少的时候没有发现这个问题，
报文头比较大，而且mDNS发现之后后续应该走TCP
而频繁的心跳应该使用UDP，所以后续改为了UDP + 自定义协议。

### 解决设备掉线卡死问题是怎么解决的？守护线程中是怎么出现死锁的和系统卡死的？
其实是ANR + 线程饥饿，并不是死锁。
排查：首二分法先加Log日志看掉线之后看那里没走了，
定位到读写锁，然后给所有的锁获取和归还加上了封装，排查到守护线程里面有一处没有归还，
就是他耦合了在守护线程里面去请求屏幕信息。
如果主备任意掉线，就会请求卡死，而且OKHttp请求是300秒超时。
并且定时线程池是3秒一次轮询检查， 然后我发现线程池的拒绝策略是：CallerRunsPolicy 
导致大量的请求被线程池拒绝，然后丢到了Android主线程，造成的ANR。

我修改OKhttp的超时时间改为5s，超时则认为设备掉线。
然后将拒绝策略改为DiscardOldestPolicy，这样就算再有任何拒绝都不会丢给主线程，而是丢弃掉最老的任务。

## CA前面板控制App + ColorPlayer播控程序App

### 前面板CA控制是怎么将Android的UI重构为Jetpack Compose的UI的，为什么要这么做？

首先说明为什么要这样做：
1. 声明式UI的组合函数声明周期直接适配，摒弃复杂的Fragment
2. 只需要一个Activity + NavHost + NavController，摒弃复杂的Activity跳转以及Intent传参
3. MVI UI自定义程度高，而且天然适配MVI设计模式
4. MVI单线数据流比MVVM调试更加方便

然后说怎么做的：
首先要规定UiIntent，UiState，UiEvent；
用户点击用Intent处理函数接收，然后处理之后改变UiState，
UiState在VM中是MutableStateFlow可写读，
对外提供是的只可读的：StateFlow

产生的副作用流是：uiEvent用MutableSharedFlow接收
然后对外提供SharedFlow，不存储的。

在Page中，一般用LaunchedEffect接收副作用流并处理。
如果有销毁则使用DisposableEffect

UiState对外暴露使用的是collectAsStateWithLifecycle
因为这个会绑定声明周期，不会在后台疯狂重构View

### 你是怎么解决RK无法播放的兼容性问题的？

* 原因：YUV422/YUV444等像素格式无法使用RK芯片上的Android系统自带的MediaPlayer播放。

* 解决方案：
  * 确认RK的产品规格书，确认规格，然后用FFmpeg去获取视频数据。
    * 检查如果支持就用RK原生的MMP硬件解码 + MediaPlayer播放流程
    * 如果不支持则改用FFmpeg 走 CPU软解码 + OpenGL渲染。
      * 之前渲染走的是Android的SurfaceView；如果是不支持则走OpenGL的GLSurfaceView
      * 然后使用GLES20进行将YUV数据转为RGB渲染。
  * 软解是非常吃性能的，现在还在讨论是ffmpeg预先转码还是用ffmepg软解码 + OpenGL渲染。
